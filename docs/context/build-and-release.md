# Build, packaging and release

Native builds, runtime and Moonshine, Linux engine and Docker, installer, updates, the release pipeline and the privacy check. Code and tests outrank this page.

| Path | Holds |
| --- | --- |
| `crates/core/examples/` | `stream_crosstalk` (checks streams don't affect each other) |
| `crates/app/examples/` | Spikes, benchmarks and diagnostics: `footprint` (RAM, VRAM, CPU, latency and word error rate per model on a folder of `.wav` + `.txt` pairs, e.g. 200 LibriSpeech test-clean utterances kept in `data\live-captions\`; `--table` prints the README table; `gpu:fp16` runs a given precision; `--hotwords "A,B:2.5"` decodes listening for words, a boost after a colon; `--heard <file>` writes what each utterance was heard as), `loopback_probe`, `asr_bench`, `play_wav`, `list_sessions`, `mic_probe` (records and levels the mic), `key_probe` (prints every key event, raw keyboard input and HID report, e.g. to check whether a keyboard's Fn reaches Windows; run it from outside the workspace) |
| `crates/core/build.rs` | Links Moonshine and sherpa-onnx's ONNX Runtime from `third_party/` for the target OS. On Windows it puts the runtime and CUDA DLLs next to the binaries; on Linux and macOS sherpa-onnx copies the runtime there and an rpath finds it. Doc tests run from a temp folder, so they need the runtime on `PATH` / `LD_LIBRARY_PATH` |
| `scripts/build-moonshine.ps1`, `.sh` | Builds Moonshine from a pinned source commit plus `patches/`, into `third_party/`: on Windows with `.ps1` (with `__FILE__` trimmed to the source folder, so no local path is compiled in), on Linux and macOS with `.sh` (static, on sherpa-onnx's ONNX Runtime). Run before `cargo build` |
| `spikes/` | Throwaway test crates kept out of the workspace (private, gitignored) |
| `scripts/fetch-runtime.ps1` | Fetches sherpa-onnx's CUDA-enabled Windows libraries, whose ONNX Runtime (1.28) Moonshine also links, so one runtime serves every model, plus NVIDIA's redistributable CUDA 12 / cuDNN 9 DLLs for the GPU option (~3 GB; `-CpuOnly` skips them, as release builds don't ship them). For the PC's own architecture: x64, or ARM64 (sherpa-onnx's CPU package only; no NVIDIA there); `build-moonshine.ps1` and `build-release.ps1` follow it too, so builds are native. Run before `cargo build` |
| `scripts/fetch-runtime.sh` | Linux twin of `fetch-runtime.ps1`: sherpa-onnx's `cuda-12.x-cudnn-9.x-onnxruntime1.28.2-linux-x64-gpu` package pinned by URL and sha256, its `lib/` unpacked into `third_party/sherpa-onnx/lib`; no NVIDIA libraries (the system or the image brings CUDA) |
| `scripts/pack-linux.sh`, `HOSTING.md`, `scripts/notices.py --engine` | Builds `kiku-engine` for Linux x64 in release mode (paths remapped as `build-release.ps1` does) and packs `target/dist/kiku-engine-<version>-linux-x64.tar.gz`, which unpacks to `kiku-engine/`: the stripped binary, ONNX Runtime and sherpa-onnx libraries (not TensorRT's provider) found through `$ORIGIN`, `HOSTING.md` (downloading models, `--serve`, the GPU's needs, Docker, a systemd service, Tailscale), `LICENSE.txt` and `THIRD-PARTY-NOTICES.txt`; fails if `ldd` finds a library missing. Built on Ubuntu 22.04, so glibc 2.35 or newer runs it |
| `Dockerfile` | The host as an image on `nvidia/cuda:12.9.1-cudnn-runtime-ubuntu22.04`, built from the release tarball (`docker build -f Dockerfile <folder with the tarball>`): runs as uid 10001, `/data` is its volume (models in `/data/models`, the host's state in `/data/host`), serves on 7300. `release.yml`'s `image` job pushes it as `ghcr.io/<owner>/kiku-engine:<version>` and `:latest` |
| `scripts/linux-build.Dockerfile`, `scripts/linux-gate.ps1` | The Linux build environment (Ubuntu 22.04, C++ toolchain, CMake, Rust), used by CI's Linux job and by the gate: `linux-gate.ps1` (private, gitignored) builds and tests in that image with `third_party`, `target` and Cargo's cache in Docker volumes of their own, then checks the tarball in clean `ubuntu:22.04` and `debian:12` containers |
| `scripts/make-fp16.py` | Converts a NeMo transducer's fp32 ONNX files to fp16 (inputs and outputs kept fp32), for models with no published fp16 export. `uv run` it: its pinned onnx and onnxruntime give the catalog's exact bytes. Check the result's WER with `footprint` |
| `scripts/install.ps1` | Copies, with robocopy, only the files of the release build (app, MCP server, GPU helper, DLLs) and models that are new or changed to `%LOCALAPPDATA%\Programs\kiku`, with a Start menu shortcut. `-Small` installs what a new user gets (no models, no GPU pack: about 45 MB), `-Target` elsewhere. The workspace folder carries a Low integrity label (agent sandbox), so binaries run from it are blocked from adding a tray icon and writing `%APPDATA%`; run the installed copy |
| `crates/core/src/update.rs` | Updates published as Kiku's releases: `<releases>/latest/download/latest.json` (`latest-arm64.json` for ARM64 builds; version, installer URL, size, sha256, `moved_to`, notes) with an ed25519 signature over those fields; the releases' address (`https://github.com/<owner>/kiku/releases`, GitHub's layout) and the public key are compiled in from `KIKU_RELEASES` and `KIKU_UPDATE_KEY` (CI sets both; a build without them never checks). `watch` checks at most once a day (the time kept in `%APPDATA%\kiku\update-checked.txt`), only after setup and with the setting on, and sends nothing else; a signed `moved_to` names the address to use from then on (kept in `update-releases.txt`, and used for the catalog's `{releases}` too); Settings → General's Check now checks at once (`check_now`, counting as the day's check) and says whether this is the latest or why it couldn't; a newer signed version goes to the panel, which offers Update / Later, downloads the installer to `%TEMP%\kiku-update`, checks size and sha256, starts it with `/SILENT` and quits |
| `installer/` | `kiku.iss`, the Inno Setup installer (`/DArch=x64` or `arm64`, `Kiku-<version>-<arch>-setup.exe`; the x64 one also installs on ARM64): per user, no admin, `%LOCALAPPDATA%\Programs\Kiku`, a Start menu shortcut and an uninstall entry (which offers to delete transcripts, settings and models), packing `target\dist\Kiku`. Silent runs (updates) wait for Kiku's `Local\Kiku` mutex, and start Kiku again. Each file is moved aside just before its new copy is written, since a running MCP server or model helper holds its exe and DLLs, which can't be replaced but can be renamed; the old copies are deleted once installed (those in use at the next update), and put back if setup fails, which starts the old Kiku again. The repository's MIT `LICENSE` is its licence page (and ships as `LICENSE.txt`); `notices.txt` heads `THIRD-PARTY-NOTICES.txt` |
| `scripts/build-release.ps1` | Release build into `target\dist` (`-Test` runs the tests first): Rust paths remapped, C `__FILE__` trimmed, PDB path a bare name; stages `target\dist\Kiku` with what a new user gets (the `install.ps1 -Small` set), the Visual C++ runtime app-local and `THIRD-PARTY-NOTICES.txt` (`scripts/notices.py`: the header plus the licences of Moonshine's built-in libraries and every Rust crate shipped) |
| `scripts/privacy-gate.py`, `scripts/ci/privacy.py`, `.githooks/`, `scripts/ci/hooks.py`, `.private-words` | Fails a commit, a push or a release if any public file (the tracked files, the binaries, the installer, `latest.json`; as bytes or UTF-16) holds a user or home folder, a Cargo home, an email address, this CI's workspace path, a tool credited as an author, or a private word: `KIKU_PRIVATE_WORDS` and this machine's user and computer names. `.private-words` (gitignored, never committed) holds the author's former names base64-encoded, so they appear nowhere in plain text; the hooks and `mise run check` read it, and CI has it as the secret `KIKU_PRIVATE_WORDS`. The public account's name is meant to show. How the hooks work: `docs/context/ci.md` |
| `README.md`, `LICENSE`, `.github/workflows/main.yml`, `.github/workflows/release.yml`, `scripts/release.py`, `scripts/publish-release.ps1`, `scripts/publish-models.ps1` | Open source (MIT), developed and released in the public `TannhauserCommons/kiku`, `main` as the trunk. A push to `main` runs `main.yml`: the checks, both Windows installers (x64 and ARM64, each built and tested on its own architecture) and, in a Linux job (Ubuntu 22.04, inside `scripts/linux-build.Dockerfile`'s image, `third_party` cached), `kiku-core`'s tests and the Linux tarball, gated unpacked (`privacy-gate.py` accepts the upstream `libonnxruntime*.so` and `libsherpa-onnx*.so` by name, `UPSTREAM`, checking them for `KIKU_PRIVATE_WORDS` only); a green commit is the release candidate. The owner runs `release.yml` by hand on `main` in the `release` environment: it signs a manifest per architecture (`release.py`, run with `uv`: `latest.json` for x64, `latest-arm64.json`), gates the manifests and publishes the candidate's draft (`ci:publish`, the tag last), made latest once complete, its notes saying which download is which, each installer also as `Kiku-setup.exe` and `Kiku-arm64-setup.exe` and the tarball as `kiku-engine-linux-x64.tar.gz`; an `image` job then pushes the Docker image to ghcr.io with `packages: write` (a new package starts private: the owner makes it public once); `publish-models.ps1` puts model files the catalog serves from there in `models-v1` once. `README.md` is the public face (features, download, building). Commits carry no tool attribution (the hooks check) |
| `patches/moonshine-*.patch` | Our changes to Moonshine. `per-stream-vad`: each stream gets its own Silero VAD instead of one shared, stateful global. `vad-segment-copy`: the detector gives the segment in progress its audio once per call instead of copying it every 32 ms. `static-unix`: static build for Linux and macOS; the Windows build is unchanged |
| `third_party/` | Moonshine source and build, sherpa-onnx libraries, CUDA runtime DLLs. Not committed |
| `models/` | Downloaded model files: Moonshine under `en/`, sherpa-onnx models and `silero_vad.onnx` under `sherpa/`. Not committed |
| `.loop/`, `scripts/*-gate.*`, `scripts/setup-release.ps1`, `AGENTS.md`, `skills/`, `spikes/` | Private agent and release material, gitignored and never committed (the `BEGIN private` block of `.gitignore`); they stay on the owner's disks and are not described here |
